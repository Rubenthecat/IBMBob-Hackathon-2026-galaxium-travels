# Plan #2 — IBM Cloud Code Engine Deployment Fixes

## Top-Level Overview

**Goal:** Make the IBM Cloud Code Engine deployment production-ready for a live hackathon demo. Judges will arrive at an unpredictable time. The app must be at $0 cost when idle, wake on the first request with a sub-15s cold start, stay warm for 30 minutes after the last request before scaling back to zero, and serve a friendly "warming up" page to users who arrive during a cold start.

**Scope:** Three IBM deploy/status scripts and the frontend Nginx container.

- [`scripts/ibm/deploy-to-ibm.sh`](scripts/ibm/deploy-to-ibm.sh) — the primary deploy script
- [`scripts/ibm/deploy-to-ibm-simple.sh`](scripts/ibm/deploy-to-ibm-simple.sh) — the simplified variant
- [`scripts/ibm/check-ibm-status.sh`](scripts/ibm/check-ibm-status.sh) — the status check utility
- [`booking_system_frontend/nginx.conf`](booking_system_frontend/nginx.conf) — hardcodes Docker Compose DNS; also handles cold-start error pages
- [`booking_system_frontend/Dockerfile`](booking_system_frontend/Dockerfile) — needs entrypoint for runtime nginx templating
- `booking_system_frontend/warming-up.html` — new static page served during backend cold start

**What is NOT in scope:** AWS scripts, Terraform, application logic, tests.

### Sub-Task 1 — Fix nginx.conf to use a configurable backend upstream

**Status:** `[ ] pending`

**Intent:**
[`nginx.conf`](booking_system_frontend/nginx.conf) line 26 hardcodes `http://backend:8080`. That hostname is the Docker Compose service name and will not resolve inside Code Engine. In Code Engine, the internal app name is `galaxium-backend`. The fix is to make the upstream configurable via an environment variable (`BACKEND_URL`) injected at container startup, using a shell entrypoint script that templates `nginx.conf` before Nginx starts.

This is the most critical fix — without it, all `/api/*` requests from the frontend return 502 in Code Engine.

**Expected Outcomes:**
- When `BACKEND_URL` env var is set (e.g. `http://galaxium-backend:8080`), Nginx proxies `/api/*` to that URL.
- When `BACKEND_URL` is not set, it defaults to `http://backend:8080` so Docker Compose local dev is unaffected.
- The [`Dockerfile`](booking_system_frontend/Dockerfile) uses an entrypoint shell script that runs `envsubst` on `nginx.conf` before calling `nginx -g 'daemon off;'`.
- `docker compose up` continues to work unchanged (no env var needed — default applies).
- Code Engine deployment passes `--env BACKEND_URL=http://galaxium-backend:8080` when creating/updating the frontend app.

**Todo List:**
1. Update [`booking_system_frontend/nginx.conf`](booking_system_frontend/nginx.conf) line 26: replace `set $backend_upstream http://backend:8080;` with `set $backend_upstream ${BACKEND_URL};` and add a default `ENV BACKEND_URL=http://backend:8080` fallback mechanism.
2. Create [`booking_system_frontend/docker-entrypoint.sh`](booking_system_frontend/docker-entrypoint.sh): a small shell script that runs `envsubst '${BACKEND_URL}' < /etc/nginx/conf.d/default.conf.template > /etc/nginx/conf.d/default.conf` then `exec nginx -g 'daemon off;'`.
3. Update [`booking_system_frontend/Dockerfile`](booking_system_frontend/Dockerfile):
   - Add `ENV BACKEND_URL=http://backend:8080` (default preserves Docker Compose behaviour)
   - Copy `nginx.conf` as `default.conf.template` (not `default.conf`)
   - Copy `docker-entrypoint.sh` and make it executable
   - Change `CMD` to use the entrypoint script instead of calling nginx directly
4. In [`scripts/ibm/deploy-to-ibm.sh`](scripts/ibm/deploy-to-ibm.sh) `deploy_frontend` function: add `--env BACKEND_URL="http://${BACKEND_APP}:8080"` to both the create and update calls.

**Relevant Context:**
- [`booking_system_frontend/nginx.conf`](booking_system_frontend/nginx.conf) line 26: `set $backend_upstream http://backend:8080;`
- [`booking_system_frontend/Dockerfile`](booking_system_frontend/Dockerfile) line 26: `COPY nginx.conf /etc/nginx/conf.d/default.conf`
- `nginx:alpine` ships `envsubst` (part of `gettext`) — available without any additional install.
- Docker Compose DNS: `backend` resolves to the backend container. Code Engine internal DNS: `galaxium-backend` resolves within the project.
- The `BACKEND_APP` variable is already defined in `deploy-to-ibm.sh` at line 23 as `${APP_PREFIX}galaxium-backend`.

### Sub-Task 2 — Fix CORS, scale-down-delay, and Java validation in deploy-to-ibm.sh

**Status:** `[ ] pending`

**Intent:**
Three independent bugs in the primary deploy script that each affect the live demo:

1. **CORS (G2):** Code Engine public URLs are always HTTPS. The backend's `CORS_ORIGINS` env var currently only includes the HTTP variant of the frontend URL. Browser requests from `https://` to the backend will be rejected by CORS middleware.
2. **Frontend scale-down-delay (G3):** Backend and Java service both get `--scale-down-delay 1800` (30 minutes), but the frontend does not. This means the frontend scales to zero far sooner than the backend, causing the frontend to cold-start while the backend is still warm — an inconsistent user experience.
3. **Java external validation (G4):** The `validate_deployment` function curls `$JAVA_URL/api/v1/health`. The Java service has `--visibility project`, meaning it is not reachable from outside Code Engine. This curl will always fail or return a connection error, producing a misleading warning in the deploy output.

**Expected Outcomes:**
- After deployment, browser requests from the frontend HTTPS URL to the backend do not fail CORS checks.
- Frontend, backend, and Java service all scale to zero at the same time (after 30 minutes of no traffic).
- `validate_deployment` does not attempt an external HTTP call against the internal Java service. Instead it tests the Java health endpoint indirectly via the backend proxy endpoint (`$BACKEND_URL/quotes` or similar) or simply skips the direct Java test with an informational note.

**Todo List:**
1. In `update_backend_cors` (line 449): change `--env CORS_ORIGINS="$FRONTEND_URL"` to `--env CORS_ORIGINS="${FRONTEND_URL},https://${FRONTEND_URL##http://}"` — this adds the HTTPS variant without duplicating if the URL is already HTTPS.
2. In `deploy_frontend` create block (lines 423–431): add `--scale-down-delay "$BACKEND_SCALE_DOWN_DELAY"` between `--max-scale` and `--wait`.
3. In `deploy_frontend` update block (lines 411–419): add `--scale-down-delay "$BACKEND_SCALE_DOWN_DELAY"` between `--max-scale` and `--wait`.
4. In `validate_deployment` (lines 497–507): replace the direct Java curl with a comment explaining it is internal-only, and instead validate the Java service is reachable from the backend by curling `$BACKEND_URL/quotes` with a POST body or testing `$BACKEND_URL/` and noting Java health is tested indirectly.

**Relevant Context:**
- [`scripts/ibm/deploy-to-ibm.sh`](scripts/ibm/deploy-to-ibm.sh)
- `BACKEND_SCALE_DOWN_DELAY` is already defined at line 38 as `"1800"` — reuse this variable for the frontend.
- Java service `--visibility project` is set at lines 359 and 374.
- CORS middleware in the backend reads the `CORS_ORIGINS` env var (see [`booking_system_backend/server.py`](booking_system_backend/server.py)).

### Sub-Task 5 — Add a cold-start "warming up" page served by Nginx

**Status:** `[ ] pending`

**Intent:**
When a judge hits the frontend URL and the backend is cold (Code Engine is spinning it up), the frontend loads fine but every API call to `/api/*` returns a `502 Bad Gateway` from Nginx — because the backend container isn't ready yet. Without intervention, the user sees a blank page, a browser error, or a perpetual spinner.

The fix lives entirely in Nginx and a single static HTML file. Nginx has a native `error_page` directive that intercepts gateway errors (502, 503, 504) and serves a custom page instead. The warming-up page auto-refreshes after 60 seconds with a `<meta>` tag, by which time the backend will be warm.

No new infrastructure. No new Code Engine apps. No extra cost. This works because:
- Nginx is already running (frontend cold start is ~5s — fast)
- The warming-up page is a static file served directly from Nginx's filesystem
- Code Engine buffers the initial request while Nginx starts, so the user never sees a raw 503

**Expected Outcomes:**
- Any `502`, `503`, or `504` response from the backend proxy is intercepted by Nginx and replaced with `warming-up.html`.
- The page shows the message: *"Starting up application... Please wait ~60 seconds and refresh. (This Hackathon user is trying to save money)"*
- The page uses the Galaxium space theme (dark background, styled with inline CSS matching the app's palette) so it looks intentional, not broken.
- After 60 seconds, `<meta http-equiv="refresh" content="60">` auto-reloads the page, which by then will either show the app or another warm-up cycle.
- Local Docker Compose dev is unaffected — the page only appears when the backend is genuinely unreachable.

**Todo List:**
1. Create `booking_system_frontend/warming-up.html` — a self-contained HTML file with:
   - Inline CSS using the Galaxium dark space theme (`#0a0a1a` background, `#6366f1` accent colour matching the app's Tailwind config)
   - The exact message: *"Starting up application... Please wait ~60 seconds and refresh. (This Hackathon user is trying to save money)"*
   - A `<meta http-equiv="refresh" content="60">` tag for auto-reload
   - A visible countdown or spinner so the user knows something is happening
   - No external dependencies (no CDN, no fonts) — fully offline-capable static file
2. Add `error_page 502 503 504 /warming-up.html;` to the `server {}` block in [`booking_system_frontend/nginx.conf`](booking_system_frontend/nginx.conf), placed before the `/api/` location block.
3. Add a dedicated `location = /warming-up.html` block in `nginx.conf` that serves the file directly from the Nginx root (`/usr/share/nginx/html/warming-up.html`) and disables proxy buffering interference.
4. Add `COPY warming-up.html /usr/share/nginx/html/warming-up.html` to the production stage of [`booking_system_frontend/Dockerfile`](booking_system_frontend/Dockerfile), after the existing `COPY --from=build` line.

**Relevant Context:**
- [`booking_system_frontend/nginx.conf`](booking_system_frontend/nginx.conf) — `error_page` directive goes inside the `server {}` block
- [`booking_system_frontend/Dockerfile`](booking_system_frontend/Dockerfile) — production stage copies assets into `/usr/share/nginx/html/`
- [`booking_system_frontend/tailwind.config.js`](booking_system_frontend/tailwind.config.js) — check this file for the exact colour palette to match
- `warming-up.html` is a build-time static file, not a template — no `envsubst` needed for it
- The `error_page` directive only fires when the proxy returns a 5xx — it does NOT fire for normal API responses, so it is safe to add alongside the existing `/api/` location block

## Implementation Order

Sub-Tasks must be executed in this order:

1. **Sub-Task 1 first** — the nginx.conf change affects the frontend Dockerfile and image. The deploy scripts (Sub-Tasks 2 and 3) add the `BACKEND_URL` env var to the frontend deploy command, which only takes effect once the new image is built.
2. **Sub-Task 5 alongside Sub-Task 1** — both touch `nginx.conf` and `Dockerfile`; doing them together avoids a second image rebuild.
3. **Sub-Tasks 2 and 3** — can be done in either order; they are independent of each other.
4. **Sub-Task 4** — fully independent, can be done at any point.

```bash
ibmcloud ce application get -n galaxium-frontend --output yaml | grep scaleDown
ibmcloud ce application get -n galaxium-hold-service --output yaml | grep scaleDown

# Verify Java is internal-only
ibmcloud ce application get -n galaxium-hold-service --output json | jq '.spec.visibility'

# Verify frontend proxy works (should return JSON, not 502)
curl -s https://<frontend-url>/api/ | jq .
```
