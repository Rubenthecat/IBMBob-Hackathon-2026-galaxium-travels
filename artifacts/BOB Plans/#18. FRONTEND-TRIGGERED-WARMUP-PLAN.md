# #18 — Frontend-Triggered Cold-Start Warm-up

## Top-Level Overview

**Goal:** When a user opens the Galaxium Travels frontend on IBM Cloud Code Engine, the frontend should automatically trigger wake-up pings to the Python backend and the Java hold service — instead of requiring the user to manually open each service's HTTPS URL in a browser to force scale-from-zero.

**Scope:**
- Add a warm-up hook in the React app that fires parallel health-check requests to both services on app load.
- The Python backend's `GET /` already returns `{"status":"OK"}` — this is the ping target.
- The Java hold service's `GET /api/v1/health` already returns `{"status":"UP"}` — this is the ping target (routed through the Python backend proxy at `/api/quotes` is not ideal; we need a direct proxy path or use the existing `/api/` prefix via nginx).
- No changes to the deploy script's scaling configuration are required — `--min-scale 0` stays.
- No new backend endpoints are needed — both health endpoints already exist.

**Non-goals:**
- Retrying until services are warm (the existing `warming-up.html` 502 fallback already handles the UX).
- Blocking the React app render until services respond.
- Changing `--min-scale` to 1 (cost implications, out of scope).

---

## Architecture

The frontend nginx container proxies `/api/*` → Python backend. The Java service is internal-only (`--visibility project`) and is only reachable through the Python backend's proxy routes. Both pings must go through `/api/`:

```
Browser → nginx /api/ → Python backend GET /        (wakes Python)
Browser → nginx /api/ → Python backend GET /health  (wakes Python; already proxied)
Python backend → Java GET /api/v1/health             (wakes Java — needs a proxy passthrough endpoint on Python)
```

Because the Java service has `--visibility project`, the browser **cannot** reach it directly. The warm-up ping for Java must be sent through the Python backend. This means the Python backend needs one thin proxy endpoint — `GET /internal/java-health` (or similar) — that calls the Java service's health endpoint and returns its result.

### Sub-Task 1 — Add Java health proxy endpoint to the Python backend

**Intent:** Expose a `GET /java-health` endpoint on the Python backend that simply calls the Java service's `GET /api/v1/health` and returns its status. This gives the browser a path to wake the Java service without directly reaching it.

**Expected Outcomes:**
- `GET /api/java-health` (via nginx `/api/` proxy) triggers the Java cold-start.
- Returns `{"status":"UP"}` when Java is warm, or a timeout/error body when still cold.
- Does not block or error-crash the backend if Java is cold — it catches exceptions and returns a graceful response.

**Todo List:**

4. On `httpx.TimeoutException` or `httpx.HTTPError`, return `{"status": "starting", "service": "java-hold-service"}` with HTTP 200 (do not propagate errors to the browser).

## Notes for Implementation

- The warm-up pings are intentionally low-cost: they hit tiny health endpoints, not data-loading routes.
- `Promise.allSettled` is the correct choice over `Promise.all` — one service being cold must not prevent the other from receiving its wake-up ping.
- The Python backend's `/java-health` proxy uses a **short** timeout (5 s) — the intent is to wake the Java pod, not to wait for it. The browser will still receive a 200 with `{"status":"starting"}` immediately if Java hasn't woken yet.
- No changes to `deploy-to-ibm.sh`, `nginx.conf`, or `docker-entrypoint.sh` are required.
